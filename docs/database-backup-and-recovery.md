# Резервное копирование и восстановление базы SportBot

## Архитектура

Рабочая база находится в `sportbot.db` (на Bothosting — обычно в `/app/data`,
если этот путь задан панелью). Приложение использует WAL и соединения из
`db_improved.py`. `backup_service.py` создаёт согласованный снимок через
`sqlite3.Connection.backup()`, поэтому `.db-wal` и `.db-shm` не копируются
отдельно и бот не останавливается.

После снимка выполняются `PRAGMA integrity_check`, открытие базы и SHA-256.
Копия считается готовой только после успешных проверок. При заданном
`BACKUP_ENCRYPTION_KEY` файл дополнительно шифруется Fernet.

## Расписание и хранение

Путь по умолчанию — `backups/`, его можно изменить через `BACKUP_DIR`.
Файлы старше 30 дней удаляются только из этого каталога. При заданном
`BACKUP_S3_BUCKET` проверенная копия и manifest загружаются по TLS в приватный
S3-compatible bucket. Включите versioning/object lock и lifecycle не короче
30 дней на стороне хранилища.

`python backup_service.py` запускает копию вручную. При работе основного
процесса также предусмотрен запуск каждые 6 часов. Для действительно
независимого расписания настройте scheduled job в панели Bothosting или
внешний runner, который запускает эту команду внутри окружения приложения.
SFTP сам по себе не запускает команды и не должен использоваться для скачивания
активного `.db`.

## Секреты

Задайте только через переменные окружения/секреты хостинга:

- `BACKUP_ENCRYPTION_KEY` — Fernet key;
- `BACKUP_S3_BUCKET`, `BACKUP_S3_ENDPOINT`, `BACKUP_S3_REGION`;
- стандартные `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY` с правами только на
  запись/чтение нужного prefix и удаление просроченных объектов.

Не добавляйте `.env`, ключи и backup-файлы в Git.

## Проверка и восстановление

Проверьте manifest, SHA-256 и наличие `integrity_check: ok`. Для зашифрованной
копии сначала расшифруйте её ключом в отдельный временный файл, затем выполните:

```bash
sqlite3 restored.sqlite3 'PRAGMA integrity_check;'
```

Остановите приложение только на короткую замену: сохраните текущую БД как
`sportbot.db.before-restore`, поместите проверенный файл во временное имя,
проверьте его ещё раз и только после явного подтверждения администратора
замените рабочий файл. Старую БД не удаляйте до успешного запуска и проверки
бота. Никогда не выполняйте тестовое восстановление поверх рабочей базы.

Перед миграцией создаётся дополнительная копия. При ошибке резервирования,
проверки или S3-загрузки исправьте причину и повторите запуск; встроенные
точки восстановления Bothosting не удаляются.
